# Legacy Skill Integration Map

This is a design map, not an authorization to edit existing skills. It keeps
the loop components small and identifies future thin hooks only after real run
records show that integration is useful.

## Hook shape

Existing skills should not absorb methodology selection, goal rendering,
readiness scoring, or run-record logic. A future hook may do one of four things:

1. provide the six pre-selection fields plus applicable controls;
2. accept an explicitly supplied `ready` handoff for work it already owns;
3. return evidence for named validation checks it actually checked;
4. require human approval before a shipping action.

No hook should automatically schedule, retry, update a skill, or convert
`review-required` into permission.

## Classification

| Role | Existing skills | Possible thin hook | Must remain outside |
|---|---|---|---|
| Producers | `task-groundwork`, `to-spec`, `triage-issue`, `prompt-creator` | Optionally emit Task, Audience, Context, Output Format, Validation, Human Review / Stop, and known controls as a loop candidate. Methodology remains selector-owned. | Readiness claims, execution, invented missing fields |
| Executors | `senior-implementer`, `tdd`, `revise-spec-from-review` | When explicitly given a `ready` handoff, surface one observation per validation check and identify evidence generated by the bounded run. | Automatic invocation, retry, scheduling, self-approval |
| Checkers | `spec-readiness`, `adversarial-spec-review`, `review-implementation`, `adversarial-diff-review` | Return check status and evidence only for checks within the reviewer’s declared coverage. Remain independent from the producer/executor. | Goal repair, readiness rewriting, record approval |
| Shipping | `commit-work`, `pr-branch` | Read the human-owned approval actions and, if later integrated, require an explicit human decision after a review-required record. | Treating `ready` or a passing record as commit/push/PR permission |
| Persistence | `session-handoff` | Carry record IDs, evidence locations, blockers, and the human-owned next action across sessions. | Creating a new run or changing the recorded result |
| Governed updater | `tune-skill` | Later consume a human-approved pattern backed by multiple run records. | Automatic skill edits from one run or maturity inference |

## Adoption order

1. Collect real records with no legacy hooks.
2. Inspect repeated handoff friction and evidence loss.
3. Choose one producer and one checker with a bounded use case.
4. Specify the smallest additive hook and its rollback.
5. Review and edit that legacy skill in a separate goal and diff.

Do not integrate every row at once. A direct, narrow one-off task may continue
to use its existing skill without entering the loop system.
