# Outcome lock

Shared ontology for `task-groundwork` (produce), `to-spec` (freeze),
`adversarial-spec-review` and `spec-readiness` (score). Each of those
skills ships this identical file as `references/outcome-lock.md`.

## Thermostat

A review closes only by calling a landed substrate or escalating the gap to
its owner. Owning a parallel machine inside the child is not closure. That
call is not lock enlargement.

**Call ≠ swallow.**

## Four lanes

Classify every material behavior as exactly one:

1. **Owned outcome** — the result this child is bound to deliver: observables,
   acceptance, and stop conditions.
2. **Substrate-call** — enter a landed owner's existing machine (API, entity,
   or protocol already responsible for this result). The child specifies the
   call and its failure path. It does not become that owner.
3. **Sibling-fence** — a neighbor's product boundary. Do not pull it forward.
   Naming the sibling owner is not a call and not ownership.
4. **Accepted residual** — a known leftover this child will not close; owner
   named or explicitly unowned.

## Discriminator

Ask: is this result already bound to the landed machine, or is a neighbor's
product boundary being pulled forward?

- Already bound → **substrate-call** (or **owned outcome** if this child is
  that owner).
- Neighbor's product pulled forward → **sibling-fence**, or Open K2.

Landed inventory is not authority to swallow a neighbor's outcome. A missing
local interface is not a ban on the call; it is Open K2.

## Parallel machine vs entry

`create` / `replace` / `cancel`, a new durable store, a new lifecycle, or a
new recovery protocol, as a **machine this child owns**, is forbidden without
`own-in-child` (a new task identity) or a new catalog task.

Entering a landed owner's create/replace/cancel **entry** is a substrate-call
when that owner already binds the result. The ban is invention of a parallel
machine, not the owner's front door.

A reviewer's `necessity=` stamp is not lock authority.

## Open K2 enum

When a human decision remains, ask exactly one question whose options are
only:

- `call-substrate` — bind to the named landed owner; this child specifies the
  call and its failure path
- `own-in-child` — new task identity: this child becomes owner of a new machine
- `defer-new-child` — a later sibling owns it; this child fences it
- `stop` — do not proceed

Do not offer a free-form menu. `own-in-child` is a new task identity, not a
silent scope add. If recovery or state owner would change and no lane is
selected, Open K2 is not `none`.
