Observed failure: the PR skill's non-technical section still used internal
terms such as retry scheduling and function names. It also reduced a broad,
mostly invisible engineering effort to a narrow technical summary, so a
manager could not understand either the outcome or the amount of work.

Required behavior: explain the verified before-and-after, reach, breadth, and
user or operational result in ordinary language before presenting technical
implementation details.

Second observed failure: a later rewrite had removed the original separate
non-technical and technical PR blocks. A PR then led with an internal-control
title, reduced the manager section to two dense paragraphs, and omitted the
verified engineering footprint even though GitHub showed 9 commits and 27
changed files. The result was technically accurate but did not make the work
or its seriousness visible in a screenshot shared with managers.

Required behavior: restore the original non-technical block (`What This PR
Does`, `The Problem`, `The Solution`, and `What Changes for the Team`) and the
separate technical block (`Technical Summary`, metric table, risk boundaries,
and `Test Plan`). Fix only the technical-language leakage in the first block;
do not replace or collapse the two-block design.

Third observed failure: the rewritten contract treated an explicit pr-branch
invocation as ambiguous between drafting and opening. The user invokes this
skill to open a PR. Invocation must therefore authorize PR creation and any
necessary non-force push; description-only mode applies only when explicitly
requested.

Fourth observed failure: restoring the two blocks and adding 9 commits, 27
files, additions, and deletions still did not make the engineering visible to
management. Those numbers describe activity, not value. A month of invisible
security and payment work can still look smaller than a cosmetic button change
unless the non-technical block explains the consequence avoided, business
breadth protected, guarantees established, failure variations covered,
operational capability gained, and downstream work safely enabled.

Required behavior: keep Git activity in the technical record or as secondary
support only. Make the non-technical block independently communicate why the
work matters and what the organization can now trust, prevent, verify, or do.
The title and manager screenshot must not depend on commit, file, or line counts
to signal importance.
